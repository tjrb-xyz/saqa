# Streaming (from dsper's docs/research/DIGEST.md §streaming)

A copy of the research digest's streaming section at dsper@7afd988, kept for its sources and reasoning. Paths and names in it are dsper's.

## streaming
- [confirmed] CamillaDSP (current v4.1.3, released 2026-04-09) supports exactly one capture and one playback device per instance. Playback types are Alsa, CoreAudio, Wasapi, Asio, Jack, Pulse, PipeWire, File and Stdout. Stdout writes raw interleaved samples in the configured `format` (S16_LE…F64_LE) and, with `wav_header: true`, a streaming WAV header whose length field is a dummy value (not allowed with S24_4_RJ_LE). (src: https://github.com/HEnquist/camilladsp/blob/master/README.md (sections 'File, RawFile, WavFile, Stdin, Stdout'; 'Device Limitation'); https://github.com/HEnquist/camilladsp/releases) → A stream cannot be a second output of the instance that drives the speakers. dsper needs an explicit Tap stage. The simplest cross-platform tap is `playback: {type: Stdout, format: F32_LE, wav_header: true}` piped into `ffmpeg -f wav -ignore_length 1 -i pipe:0 …`, or raw with `-f f32le -ar 48000 -ac N -ch_layout <layout> -i pipe:0`.
- [confirmed] `enable_rate_adjust` works only with ALSA, Wasapi, CoreAudio, PipeWire or ASIO playback devices, not File/Stdout. When enabled, CamillaDSP first tries capture-device clock tuning, which is bit-perfect and needs no resampler. That is supported for ALSA Loopback, the USB Audio Gadget and BlackHole 0.5.0+. It falls back to an Async resampler, and failing both, drift is left uncorrected. (src: https://github.com/HEnquist/camilladsp/blob/master/README.md ('enable_rate_adjust'; 'How CamillaDSP applies the correction')) → A Stdout 'stream instance' has no clock of its own and is paced by its capture device. When the speaker instance uses clock tuning on the dsper virtual endpoint, the endpoint's clock is slaved to the DAC, so any other reader of that endpoint (the stream instance) also runs at the DAC's rate. The custom BlackHole-derived device must keep BlackHole's clock-tuning control, or this bit-perfect path is lost. Only one client can own that tuning.
- [confirmed] CamillaDSP applies the default `Main` fader volume to every channel at the start of the pipeline (`Pipeline::process_chunk` runs `self.volume.process_chunk` before any mixer or filter step). The four extra faders Aux1–Aux4 are available only through explicit `Volume` filters. (src: https://github.com/HEnquist/camilladsp/blob/master/src/pipeline.rs ; README 'Volume control' section) → Any stream channels produced by the same pipeline inherit the listener's volume knob and mute. For a broadcast-grade tap, dsper should pin Main at 0 dB and put local listening volume on an Aux fader applied only to the speaker channels, unless the owner literally wants the stream to follow the room volume. This must be a stated policy.
- [confirmed] CamillaDSP's `Limiter` filter is a hard or soft clipper at `clip_limit` dB with no lookahead or oversampling. The `Compressor` processor has an optional clip stage. (src: https://github.com/HEnquist/camilladsp/blob/master/README.md ('Limiter', 'Compressor')) → It is not a true-peak limiter. Meeting a -1 dBTP ceiling at the codec input needs an oversampling or true-peak limiter elsewhere in the stream path (for example FFmpeg loudnorm, or a dedicated external stage).
- [confirmed] The CamillaDSP websocket exposes sample-peak and RMS metering (GetPlaybackSignalPeak/Rms and the …Since/…SinceLast variants, GetSignalLevels), plus GetCaptureRate, GetRateAdjust and GetStopReason. It has no LUFS or true-peak metering. (src: https://github.com/HEnquist/camilladsp/blob/master/websocket.md) → The web UI's broadcast loudness meter must come from another component, for example FFmpeg's `ebur128` filter with `peak=true` and `metadata=1`, or libebur128.
- [confirmed] CamillaDSP 4.0.0 (2026-03-19) added a native PipeWire backend. It creates filter nodes with `node_name`, `node_description`, `node_group_name` and `autoconnect_to`, and nodes in one group are scheduled by the same driver. The PipeWire docs state 'A port can be linked to many other ports and PipeWire will manage mixing and duplicating the buffers.' (src: https://github.com/HEnquist/camilladsp/blob/master/backend_pipewire.md ; CHANGELOG.md v4.0.0 ; https://github.com/PipeWire/pipewire/blob/master/doc/dox/internals/library.dox) → On PipeWire hosts, the cleanest 'what you hear is what you get' tap is to link CamillaDSP's playback node to both the hardware sink and an encoder client, e.g. `pw-record --raw --target <node> --channels N -` | ffmpeg. Both get the same samples in the same graph cycle on the same clock, with no extra instance and no resampling.
- [confirmed] snd-aloop supports 1–32 channels and 8 kHz–768 kHz, and has `pcm_substreams` (1–8), `pcm_notify` and a `timer_source` module parameter. `timer_source` clocks the loopback from a named sound card's timer instead of jiffies or hrtimer. (src: https://github.com/torvalds/linux/blob/master/sound/drivers/aloop.c) → Pure-ALSA tap: CamillaDSP plays to an ALSA `multi` PCM that binds the hardware card plus an aloop device with `timer_source` set to that card, and the encoder reads the aloop capture side (`ffmpeg -f alsa -ac N -i hw:Loopback,1`). The alsa-lib `multi` plugin does not synchronise its slaves itself, so timer_source is what makes this sample-locked.
- [confirmed] PipeWire ships an AES67 configuration (pipewire-aes67.conf): a PTP driver node (`clock.name = clock.system.ptp0`), `module-rtp-sap` using the ptp4l management socket, and `module-rtp-sink` with `sess.min-ptime = 1`/`sess.max-ptime = 1`. module-rtp-sink also supports `sess.media = opus`. (src: https://github.com/PipeWire/pipewire/blob/master/src/daemon/pipewire-aes67.conf.in ; src/modules/module-rtp-sink.c) → On Linux, dsper can offer an AES67 output (into a radio studio's AoIP) by configuring PipeWire rather than implementing RTP/PTP/SAP itself. This needs linuxptp and a NIC with suitable timestamping.
- [confirmed] AES67 mandates a 1 ms packet time (0.125/0.25/0.5/4 ms are optional), L24 at 48 kHz, PTPv2 (IEEE 1588-2008) clocking and SDP stream description, with up to 8 channels per stream at 1 ms. At 1 ms, 16 ch × 48 samples × 3 bytes = 2304 bytes of payload, which exceeds a 1500-byte MTU. (src: https://en.wikipedia.org/wiki/AES67 (via search snippet; aes.org blocked) ; arithmetic) → A 16-channel AES67 feed must be two 8-channel streams, or use a shorter optional ptime. AES67 is LAN or studio only (multicast plus PTP), so it is the right answer for feeding a station's console, not for internet delivery.
- [confirmed] EBU Tech 3326 (N/ACIP) is the interoperability baseline for broadcast contribution codecs (Comrex, Tieline and others): SIP signalling, RTP over UDP and SDP, with G.711, G.722, MPEG-1 Layer II and linear PCM as mandatory codecs. (src: https://tech.ebu.ch/publications/tech3326 (via search snippet; site blocked)) → To land in a station's contribution codec rather than its Icecast, the interoperable path is SIP/RTP with MP2 or PCM. This is a later-phase sink, not v1.
- [confirmed] Icecast is codec-agnostic at the transport level. It parses Ogg (Vorbis, Opus, FLAC, Speex, Theora, Kate) and WebM/Matroska natively, and handles everything else, including audio/mpeg and AAC, with a 'generic' fallback handler. For Opus and FLAC it only reads the channel count for stats. The latest stable release is 2.5.0 (2025-12-31), the first since 2.4.4 (2018). (src: https://github.com/xiph/Icecast-Server/blob/master/src/format.c , src/format_opus.c, src/format_flac.c ; https://icecast.org/news/icecast-release-2_5_0/ (search)) → A 16-channel Ogg Opus (family 255) or WebM stream passes through Icecast unchanged. Channel limits come from the codec and from players, not the server.
- [confirmed] Source clients connect to Icecast 2.4.0+ with HTTP PUT and a required Content-Type; older servers use the legacy SOURCE method. FFmpeg's `icecast://[user[:pass]@]host:port/mount` protocol takes `ice_name`, `ice_description`, `ice_genre`, `ice_url`, `ice_public` (default 0), `content_type` (must be set unless audio/mpeg), `legacy_icecast` and `tls`. (src: https://github.com/FFmpeg/FFmpeg/blob/master/doc/protocols.texi (Icecast section) ; Icecast NEWS 2.4.1 'Require Content-Type header for PUT requests') → A minimal dsper sink is `ffmpeg … -c:a libopus -f ogg -content_type audio/ogg icecast://source:PASS@host:8000/mount`. Keep `ice_public=0` as the default so nothing is listed in public directories without the owner's consent.
- [confirmed] Icecast defaults are burst-size 64 KiB and queue-size 500 KiB (maximum 16 MiB). It supports `<fallback-mount>`, `<fallback-override>` and `<fallback-when-full>`. (src: https://github.com/xiph/Icecast-Server/blob/master/src/cfgfile.c ; conf/icecast.xml.in) → Listener start-up latency depends on bitrate: 64 KiB is about 4 s at 128 kbit/s and about 1 s at 512 kbit/s, plus player buffering. Icecast cannot serve interactive monitoring. Fallback mounts are the standard 'always available' mechanism when dsper's source drops.
- [confirmed] SHOUTcast DNAS 2.x carries MP3 and AAC/AAC+ only, with v1 (ICY) and v2 (Ultravox 2.1) source protocols. There is no Ogg, Opus or FLAC. (src: https://www.rocketbroadcaster.com/docs/technical-specification.html ; https://www.cloudrad.io/help/shoutcast-vs-icecast-vs-hls (secondary, via search)) → A SHOUTcast target means a stereo MP3/AAC profile. Multichannel is effectively unavailable on SHOUTcast.
- [confirmed] MP3 through FFmpeg's libmp3lame is limited to mono or stereo (CODEC_CH_LAYOUTS(MONO, STEREO)). (src: https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/libmp3lame.c) → MP3 profiles are stereo downmixes. For a multichannel system that breaks 'what you hear is what you get' unless the downmix is a declared bus.
- [confirmed] Opus channel mapping families in libopus: 0 = mono/stereo; 1 = 1–8 channels in Vorbis order (the surround encoder uses masking and LFE optimisations); 2 (and 3) = ambisonics; 255 = up to 255 channels with no defined layout. Multistream carries at most 255 elementary streams. FFmpeg's libopus default (`-mapping_family -1`) picks 0 for ≤2 channels and 1 otherwise, and rejects more than 8 channels; family 255 is capped at 254 channels in FFmpeg. (src: https://github.com/xiph/opus/blob/main/src/opus_multistream_encoder.c ; include/opus_multistream.h ; https://github.com/FFmpeg/FFmpeg/blob/master/doc/encoders.texi (libopus mapping_family) ; libavcodec/libopusenc.c) → A 16-channel dsper stream must be encoded with `-mapping_family 255` and carries no speaker semantics, so dsper must publish its own channel map (for example in stream metadata or a sidecar). A 'listenable' surround stream should be at most 8 channels with family 1 and a declared `-ch_layout`, because FFmpeg reorders into Vorbis order from the declared layout.
- [confirmed] Opus accepts only 8, 12, 16, 24 or 48 kHz input. Snapcast notes it resamples non-48 kHz sources for Opus. (src: https://github.com/savonet/liquidsoap/blob/main/doc/content/encoding_formats.md (Opus samplerate) ; https://github.com/badaix/snapcast (doc/configuration.md)) → If the system follows a 44.1 or 96 kHz endpoint, the Opus stream is necessarily resampled and not sample-identical. A broadcast profile should pin the pipeline at 48 kHz, or use FLAC/PCM for bit-identical delivery.
- [confirmed] FLAC is limited to 8 channels (libFLAC `FLAC__MAX_CHANNELS (8u)`; FFmpeg `FLAC_MAX_CHANNELS 8`). (src: https://github.com/xiph/flac/blob/master/include/FLAC/format.h ; https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/flac.h) → A lossless 16-channel stream cannot be a single FLAC stream. Use two 8-channel FLAC streams (not mutually synchronised across independent HTTP mounts) or PCM, which is LAN-scale: 16 ch at 24-bit/48 kHz is about 18.4 Mbit/s.
- [confirmed] FFmpeg's native AAC encoder uses standard channel configurations up to 7.1 and above that a PCE, for named layouts up to 16 channels (for example 7.1.4, 9.1.4, 9.1.6; AAC_MAX_CHANNELS 16). libfdk_aac supports at most 8 channels (7.1 or 5.1.2). The FFmpeg licence notes Fraunhofer FDK AAC is GPL-incompatible. (src: https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/aacenctab.h , aacenc.c , libfdk-aacenc.c ; LICENSE.md) → 16-channel AAC is possible only by labelling channels with a speaker layout such as 9.1.6, and players may then render or downmix them. A redistributable dsper or Pi image must not bundle an FFmpeg built with libfdk_aac alongside GPL code; use the native `aac` encoder.
- [confirmed] FFmpeg's MPEG-TS muxer accepts Opus only with mapping family 0 (≤2 ch) or family 1 (≤8 ch, standard mappings), and errors on family 255. SMPTE 302M PCM in TS allows only 2, 4, 6 or 8 channels. (src: https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/mpegtsenc.c ; libavcodec/s302menc.c) → SRT and RIST normally carry MPEG-TS, so a 16-channel feed over them needs two elementary streams (2× 8-channel Opus or S302M PIDs) or a non-TS payload that receivers may not accept.
- [confirmed] libsrt's default receive latency in live mode is 120 ms (SRTO_RCVLATENCY). The negotiated latency is the larger of the two peers' values. FFmpeg's `srt://host:port?mode=caller|listener|rendezvous&latency=<µs>` has `payload_size`/`pkt_size` defaulting to 1316 (TS-sized) and `transtype=live|file`. (src: https://github.com/Haivision/srt/blob/master/docs/API/API-socket-options.md ; https://github.com/FFmpeg/FFmpeg/blob/master/doc/protocols.texi (srt)) → SRT is the robust contribution link to a station or relay: encrypted, ARQ-protected, about 120 ms or more. dsper's SRT sink should expose `latency` and `passphrase`, and support listener mode so stations can pull.
- [confirmed] FFmpeg supports RIST (`rist://`) through librist, with `rist_profile=simple|main|advanced` (default main), `buffer_size` (default 0 = librist's 1 s, maximum 30 s), `pkt_size` 1316 and `encryption` 128 or 256. (src: https://github.com/FFmpeg/FFmpeg/blob/master/doc/protocols.texi (rist)) → RIST is an alternative to SRT with the same MPEG-TS channel constraints. It is an optional sink, lower priority than SRT.
- [confirmed] WHIP is RFC 9725 (March 2025, Standards Track). FFmpeg has had an experimental `whip` muxer since 8.0 (whip.c exists at tag n8.0, not n7.1). It supports only Opus audio, stereo at 48 kHz ('Unsupported audio channels … choose stereo'), and its documented example reaches about 150 ms end to end. BUTT has streamed to WHIP servers since 1.42.0 (Opus only), and OBS has a WHIP output. (src: https://www.rfc-editor.org/info/rfc9725 (search) ; https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/whip.c , doc/muxers.texi ; https://danielnoethen.de/butt/release/1.45.0/butt-1.45.0_manual.html (search) ; https://github.com/obsproject/obs-studio/tree/master/plugins/obs-webrtc) → WebRTC/WHIP gives sub-second remote monitoring but only as a stereo bus in practice. Browser monitoring in the web UI should default to a stereo 'monitor' bus.
- [confirmed] Multichannel Opus over WebRTC is not standard: RFC 7587 is stereo, and libwebrtc/Chrome use a non-standard 'multiopus' SDP (`num_streams`, `coupled_streams`, `channel_mapping`), which is not offered by default and needs SDP munging. Janus added 5.1 hard-coded (PR #2059, 2020). GStreamer's rtpopuspay emits MULTIOPUS for more than 2 channels. An IETF individual draft (draft-shin-avtcore-rtp-multi-opus) proposes standardising it. (src: https://github.com/meetecho/janus-gateway/pull/2059 ; https://github.com/GStreamer/gstreamer/blob/main/subprojects/gst-plugins-good/gst/rtp/gstrtpopuspay.c ; https://www.ietf.org/archive/id/draft-shin-avtcore-rtp-multi-opus-01.html (search)) → Do not plan 16-channel monitoring over WebRTC. For multichannel monitoring, use WebSocket or WebTransport with Opus family 255 or PCM, decoded by WebCodecs or WASM into an AudioWorklet.
- [confirmed] A September 2026 third-party measurement (one source) found Chrome 152 and Firefox 155 decode 16-channel family-255 Opus in WebM and fMP4 via decodeAudioData and WebCodecs. Safari 27 (macOS) and Safari 18.7 (iOS) refuse both decode paths even though canPlayType/isTypeSupported report support for WebM. A WASM libopus (opus-decoder 0.7.12) decoded all 16 channels on every browser tested. (src: https://github.com/mormegil6/safari-multichannel-opus-repro (README and results/ JSON, measured 2026-09-12, re-run 2026-09-25)) → dsper's web-UI player must feature-detect by actually decoding, not by canPlayType. It needs a WASM Opus fallback for Safari and a channel picker or downmix, because a browser's output device is usually stereo. Treat as a single-source result.
- [uncertain] Safari 18.4 added Opus in Ogg (before that, Safari played Opus only in CAF), but it is reported as still incomplete or buggy. (src: https://frequal.com/java/OggOpusStillNotWorkingInSafari18_4.html ; https://github.com/kevinch3/NicotinD/issues/1254 (search snippets only)) → An Icecast Ogg Opus mount may not play in Safari's `<audio>`. Keep an AAC or MP3 stereo mount, or a JS/WASM player, for Apple listeners.
- [uncertain] Standard HLS with Apple's recommended 6 s target duration has at least about 18 s latency (typically 15–30 s). LL-HLS (partial segments of about 200 ms plus blocking playlist reload) reaches about 2–5 s. Apple's HLS authoring spec requires a stereo AAC rendition, and the listed multichannel formats centre on AC-3/E-AC-3. (src: https://datatracker.ietf.org/doc/html/draft-pantos-hls-rfc8216bis (search) ; https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices (search snippet; site blocked)) → HLS/DASH suits large passive audiences via a CDN, not monitoring or 'what you hear' checks. It is a later sink, and it could come from a relay (MediaMTX, Liquidsoap `output.file.hls`) rather than from dsperd.
- [confirmed] Enhanced RTMP v2 (release doc v2-2026-01-31-r2) adds FourCC audio codecs (AC-3, E-AC-3, Opus, MP3, FLAC, AAC), an `AudioPacketType.MultichannelConfig` packet carrying channel order and count, and multitrack. FFmpeg 8.0 lists 'Enhanced FLV v2: Multitrack audio/video, modern codec support'. MediaMTX reads Opus, FLAC, AAC, MP3, AC-3, G711 and LPCM over RTMP. (src: https://github.com/veovera/enhanced-rtmp/blob/main/docs/enhanced/enhanced-rtmp-v2.md ; https://github.com/FFmpeg/FFmpeg/blob/master/Changelog ; https://github.com/bluenviron/mediamtx/blob/main/docs/4-read/05-rtmp.md) → RTMP is the ingest path for video platforms (YouTube, Twitch; Audio Hijack's 'Live Stream' block), not for radio stations. Whether platforms accept multichannel or E-RTMP audio is unverified, so plan it as stereo AAC.
- [confirmed] FFmpeg audio inputs: `-f alsa`, `-f avfoundation` on macOS (the channel count comes from the device's `mChannelsPerFrame`), `-f pulse`, `-f jack`, and raw or WAV on `pipe:0` (the wav demuxer has `ignore_length` for streaming headers). There is no native PipeWire input device. The `tee` muxer's `onfail=ignore` keeps other outputs alive when one fails. (src: https://github.com/FFmpeg/FFmpeg/blob/master/doc/indevs.texi , doc/demuxers.texi (wav), doc/muxers.texi (tee), libavdevice/avfoundation.m) → Prefer pipe input (from CamillaDSP Stdout, or `pw-record --raw -`, which PipeWire documents as streaming raw to STDOUT with --rate/--format/--channels/--channel-map) over device capture. That avoids OS capture quirks, and one encode can fan out to several destinations with `-f tee` and `onfail=ignore`.
- [uncertain] Capturing more than 2 channels from a 16-channel CoreAudio device through FFmpeg's avfoundation delivers all channels intact. (src: https://github.com/FFmpeg/FFmpeg/blob/master/libavdevice/avfoundation.m (reads mChannelsPerFrame; not tested)) → Do not rely on avfoundation capture of the dsper virtual device on macOS. Use CamillaDSP Stdout or a native CoreAudio reader in dsperd.
- [confirmed] Liquidsoap's core PCM content type supports only mono, stereo and 5.1 (1, 2 or 6 channels; `Audio_layout.layout_of_channels` raises Unsupported otherwise). More channels need multitrack (several audio tracks). Its native `%opus` encoder accepts only 1 or 2 channels. The latest release line is v2.4.x (tag v2.4.5); 2.5.0 is unreleased on main and adds a built-in `icecast.server`. It has input.alsa, input.jack, input.pulseaudio, input.srt, input.harbor and input.ffmpeg, and output.icecast, output.srt and output.file.hls. (src: https://github.com/savonet/liquidsoap/blob/main/src/core/formats/audio_layout.ml ; doc/content/encoding_formats.md ; doc/content/multitrack.md ; CHANGES.md ; git tags) → Liquidsoap fits station-side automation, fallback and relay (for example `input.harbor` or `input.srt` to `output.icecast`), not transparent 16-channel pass-through from dsper.
- [confirmed] GStreamer: `opusenc` accepts 1–255 channels and chooses family 0, 1 or 255 automatically. `shout2send` accepts only Ogg, MP3 (MPEG-1 layers 1–3) and WebM, not AAC. `rtpL16pay`/`rtpL24pay` accept any channel count. There are `srtsink`/`srtsrc`, `ristsink`, `osxaudiosrc` (macOS), `alsasrc`, `pipewiresrc` and `fdsrc`. (src: https://github.com/GStreamer/gstreamer/blob/main/subprojects/gst-plugins-base/ext/opus/gstopusenc.c ; subprojects/gst-plugins-good/ext/shout2/gstshout2.c ; gst/rtp/gstrtpL24pay.c ; subprojects/gst-plugins-bad/ext/srt) → GStreamer is the most channel-flexible embeddable engine (for example via gstreamer-rs in a Rust daemon). An FFmpeg subprocess is simpler to supervise. Either can be dsper's 'encoder stage', given the declared-I/O external-stage model.
- [confirmed] DarkIce reads from OSS, ALSA, PulseAudio, JACK or Solaris devices and streams to Icecast/Icecast2/SHOUTcast (up to 8 outputs of each). Its Opus and Vorbis encoders accept only 1–2 channels, and its FLAC encoder requires exactly 2 channels at 16-bit. The latest tag is v1.6. (src: https://github.com/rafael2k/darkice (src/OpusLibEncoder.cpp, src/FlacLibEncoder.cpp, man/darkice.cfg.5)) → DarkIce is stereo-only legacy. Mention it as compatible, but do not build on it.
- [confirmed] BUTT (Windows/macOS/Linux, PortAudio input) streams to Icecast, SHOUTcast and WebRTC/WHIP, with channel mode stereo or mono only. Current version is 1.47.0 (2026-07-05). A `butt-client` binary sends commands to a running instance. (src: https://danielnoethen.de/butt/Changelog.html ; https://danielnoethen.de/butt/release/1.45.0/butt-1.45.0_manual.html (search snippets; site blocked)) → BUTT is a GUI stereo tool. It is useful as the 'user already has it' option (point it at the dsper endpoint), but it is not dsper's headless encoder.
- [confirmed] Snapcast v0.35.0 (project moved to github.com/snapcast/snapcast) takes sources from pipe, alsa, tcp, process, jack, pipewire, librespot and airplay. Its codecs are flac (default, about 26 ms codec latency), ogg, opus and pcm, and its Opus encoder rejects anything but 2 channels. Default end-to-end buffer is 1000 ms; sampleformat looks like `48000:16:2`. (src: https://github.com/badaix/snapcast (changelog.md, doc/configuration.md, server/etc/snapserver.conf, server/encoder/opus_encoder.cpp)) → Snapcast is prior art and a possible sink for synchronised LAN multi-room listening: feed it a pipe from the tap. Its time-synced client model is the reference for 'remote listeners hear the same thing in step'.
- [confirmed] Audio Hijack's Broadcast block streams MP3 or AAC (switching to HE-AAC at 64 kbit/s and below) to SHOUTcast or Icecast, and several blocks can run in one session. A separate Live Stream block targets RTMP services (YouTube, Twitch). Its channel-count limits were not verified. (src: https://rogueamoeba.com/support/manuals/audiohijack/?page=broadcast ; https://rogueamoeba.com/support/knowledgebase/?showArticle=AudioHijack-StreamingDifferences (search snippets)) → This is the UX benchmark for macOS: several simultaneous stream blocks at different qualities from one pipeline. dsper's Stream stage should allow N destinations per tap.
- [confirmed] OBS Studio supports at most 8 channels (speaker layouts up to 7.1; MAX_AUDIO_CHANNELS 8) and 6 audio mixes. It outputs RTMP, SRT and RIST through FFmpeg MPEG-TS, and WHIP. (src: https://github.com/obsproject/obs-studio/blob/master/libobs/media-io/audio-io.h ; plugins/obs-ffmpeg (obs-ffmpeg-srt.h, obs-ffmpeg-rist.h) ; plugins/obs-webrtc/whip-output.cpp) → OBS cannot carry dsper's full 16 channels. Its 6-mix multitrack model (several stereo buses in one stream) is a workable pattern for a 'channeled' stream.
- [confirmed] MediaMTX (MIT) accepts publishing over SRT, WebRTC, RTSP, RTMP, HLS, MPEG-TS, RTP and MoQ, and re-serves over those protocols. Readable audio codecs per protocol: WebRTC Opus/G722/G711; SRT Opus/AAC/MP3/AC-3; HLS Opus/FLAC/AAC; RTMP adds FLAC and LPCM. An `alwaysAvailable` option plays an offline segment while the publisher is gone. (src: https://github.com/bluenviron/mediamtx (README.md, docs/4-read/*, docs/2-features/08-always-available.md)) → MediaMTX is a candidate embedded or local relay: dsper publishes once (for example SRT) and MediaMTX fans out to WHEP browser monitoring, HLS and remote pulls, and keeps listeners connected across dsper restarts.
- [uncertain] macOS 14.2 introduced Core Audio process taps (`AudioHardwareCreateProcessTap` plus `CATapDescription`), which capture a process's or an output device's audio without a virtual driver and without stopping playback. CamillaDSP issue #529 (opened 2026-09-17, still open) requests this as a capture source. It is unverified whether a device-stream tap preserves more than 2 channels. Baseline corrections:
- 'Windows via gadget mode (CamillaDSP has no ASIO backend)' is out of date. CamillaDSP 4.0.0 (2026-03-19) added an optional ASIO backend (`--features asio-backend`, GPLv3-only binary, not in the prebuilt Windows zip, which is Wasapi-only). Gadget mode is still the answer for multi-device aggregates on Windows, but a single-interface Windows host running CamillaDSP over ASIO is now feasible.
- 'Linux: pure ALSA mode and a PipeWire-coexisting mode' understates what is available. CamillaDSP 4.0 has a native PipeWire backend (filter nodes with node_group_name and autoconnect_to). PipeWire mode can be first-class, and it gives the cleanest stream tap: one output port linked to both the hardware sink and the encoder, same cycle, same clock.
- The plan has no Tap concept, but CamillaDSP drives one playback device per instance, so a stream needs one explicitly. Per platform: PipeWire link fan-out; ALSA `multi` plus snd-aloop with `timer_source` set to the hardware card; a second CamillaDSP instance with `type: Stdout`; or, on macOS, a Core Audio process tap (14.2+, unverified for multichannel) or the managed aggregate with a BlackHole-derived monitor endpoint.
- The 'split' mode description ('async resampling each') is incomplete. CamillaDSP prefers capture-clock tuning, which is bit-perfect, on ALSA Loopback, the USB gadget and BlackHole ≥0.5.0. The dsper virtual device must keep that control. Only one instance can own an endpoint's clock tuning, so in split mode with several instances reading the same endpoint, at most one may tune and the rest must use AsyncSinc/AsyncPoly.
- 'Sample-rate following of endpoint nominal rate' conflicts with Opus streaming, which accepts only 8, 12, 16, 24 or 48 kHz. A broadcast or stream profile should pin 48 kHz, or accept a resampled, non-identical stream, or use FLAC (≤8 ch) or PCM for bit-identical delivery.
- 'Limiter' in the safety design: CamillaDSP's Limiter is a sample-peak clipper (hard or soft, no lookahead or oversampling). That suits driver protection, but a broadcast stream needs true-peak control (≤ -1 dBTP at codec input per EBU R128 and AES TD1008) from a separate oversampling stage.
- Presets and levels: CamillaDSP's default Main fader is applied to all channels at the start of the pipeline, so a stream derived in the same pipeline follows the listener's volume and mute. The plan must pin Main at 0 dB and move local volume to an Aux fader on speaker-only channels, or declare that the stream follows the room volume.
- 'What you hear is what you get' needs a defined tap point in crossover mode. Post-crossover outputs are per-driver feeds and are not listenable, and room-correction filters are wrong for remote listeners. Tap points should be selectable (program pre room correction, program post room correction, raw driver feeds for diagnostics), defaulting to program pre-crossover.
- The owner's '16 channels' does not travel as one standard stream. Opus family 255 is the only single-codec carrier (no speaker semantics, and Safari refuses to decode it). FLAC, MPEG-TS Opus and SMPTE 302M stop at 8 channels, MP3 at 2, and WebRTC is stereo in practice. A 'channeled' stream should be modelled as one N-channel Opus-255 stream and/or several stereo or ≤8-channel sub-streams (mounts, PIDs or tracks).
Risks:
- Backpressure coupling: CamillaDSP Stdout blocks when the pipe fills (about 64 KiB on Linux). If the encoder or network stalls, the instance stalls and local audio drops. dsperd must decouple through a bounded ring buffer that drops or fills silence on the stream side and never stalls the audio side.
- Always-available versus volatile devices: if the stream is tapped downstream of a physical-device instance, unplugging that device stops the stream. Tap upstream of volatile devices (on the stable endpoint or program bus) and keep the encoder fed with silence across reconciles. Add server-side fallback: Icecast `fallback-mount`/`fallback-override` or MediaMTX `alwaysAvailable`.
- Loudness processing (loudnorm adds about 3 s and changes dynamics) and codec resampling break sample identity. The UI must show whether a stream is bit-identical, rate-converted or mastered, or 'what you hear is what you get' becomes an unverifiable promise.
- Browser support for multichannel is fragmented. Chrome and Firefox decode 16-channel Opus; Safari refuses it (one Sep 2026 measurement) while its string APIs claim support. WebRTC is effectively stereo. The web UI needs WASM decoding and a channel picker or downmix.
- Independent streams (for example two 8-channel FLAC mounts, or several stereo mounts) are not mutually sample-aligned at the listener. Truly synchronised multichannel needs one stream, PTP/AES67 on a LAN, or a Snapcast-style time-synced client.
- 16-channel AES67 exceeds a 1500-byte MTU at the mandatory 1 ms ptime (2304-byte payload). It needs two 8-channel streams, and PTP needs linuxptp plus suitable NIC timestamping, which Raspberry Pi Ethernet may not provide well (not verified).
- Several CamillaDSP instances cannot all tune one virtual endpoint's clock, and conflicting rate-adjust owners will fight. The reconciler must assign exactly one tuning owner per endpoint.
- Licensing: an FFmpeg build with libfdk_aac is GPL-incompatible and not redistributable in a GPL Pi image. CamillaDSP ASIO builds are GPLv3-only. BlackHole-derived code is GPL-3.0. Music broadcasting needs performance or royalty licences (for example SoundExchange, PRS/PPL or GEMA, depending on country), which is the operator's responsibility. Default `ice_public=0` and make that responsibility visible in the UI.
- Security: Icecast source passwords, SRT passphrases and WHIP bearer tokens are credentials held by a daemon with a network-exposed web UI. They need a secret store, TLS (FFmpeg icecast `tls`, SRT encryption) and authenticated remote control.
- Latency expectations: Icecast takes seconds (bitrate-dependent burst plus player buffer), HLS 6–30 s (LL-HLS 2–5 s), SRT 120 ms or more, WHIP about 150–200 ms. Remote live tweaking of EQ is only usable over a WebRTC or WebSocket monitor path.
- Speaker semantics: family-1 Opus and AAC reorder channels by declared layout (FFmpeg maps from its layout to Vorbis or AAC order). Feeding raw PCM without `-ch_layout` risks silently mis-ordered surround. Family 255 carries no layout, so dsper must publish its channel map out of band.
- Unverified items that could change the macOS design: whether Core Audio process or device taps preserve more than 2 channels, and whether FFmpeg avfoundation captures more than 2 channels intact from a 16-channel virtual device.
